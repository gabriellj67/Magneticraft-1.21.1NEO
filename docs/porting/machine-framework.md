# 方块实体模块、菜单与网络框架

本阶段以 Nova 1.12 固定提交 `4108ca9bb332d11965c30e0c592b310d0858f251` 为行为依据，
用纯 Java/Forge 1.20.1 API 重建可组合的方块实体框架，并用压碎台、电池和电炉完成纵向验证。

## 模块与持久化

`MachineBlockEntity` 在构造时按稳定 `ResourceLocation` 注册模块。重复 ID 会立即失败；保存时每个
模块写入 `modules/<namespace:path>` 独立复合节点。缺失节点保留模块默认值，未知节点被忽略，
因此后续增删模块不会重新引入 1.12 `_modules` 列表的索引耦合。

框架统一转发 `onLoad`、capability invalidate/revive、服务端 tick 和更新包。持久状态变化调用
`markChanged()`；只有压碎台展示物和机器工作状态等渲染必要数据使用方块实体更新包，容器槽位、
能量和进度沿用原版 Menu 同步。

后续客户端阶段在不改变模块所有权的前提下补充了节流的渲染状态快照：流体、多方块工作状态和
可编程设备运行状态由服务端统一同步，32 位菜单值通过成对的 16 位槽传输。客户端只做有界插值，
不反向驱动服务端状态。

## 能力边界

- `ItemInventoryModule` 仅持有一个 `ItemStackHandler`，向每个方向创建受插入/抽取槽位规则约束的
  视图。压碎台不暴露物品能力；电炉只允许输入槽插入、输出槽抽取。
- `EnergyStorageModule` 以纯 Java `EnergyBuffer` 为真值，Forge Energy 只是受方向及收发权限约束
  的适配器。电池可收发，电炉的外部视图只可接收，但处理模块仍可在内部消耗能量。
- `FluidTankModule` 完成方向、持久化和 capability 生命周期契约；当前三台设备没有旧版流体行为，
  因而没有虚构流体消费者。
- `GhostFilterModule` 与 `GhostSlot` 保存计数固定为 1 的样本，不拥有真实物品。当前三台旧设备
  没有过滤槽，所以只提供通用框架和受保护的 C2S 合约。

## 设备行为

压碎台仅接受顶部主手交互，进度阈值为 40。石、铁、钢锤的等级/单击进度/耐久消耗分别为
`1/8/1`、`2/10/1`、`4/15/1`；武器命中仍单独消耗 2 点耐久。无配方、非锤交互会把台面物品
退回背包；完成后可持锤从背包补充相同输入。压碎配方改为 `magneticraft:crushing` 数据配方。

电池容量为 1,000,000 FE，两个槽分别给物品充电和从物品放电，每向每 tick 最多 500 FE。
小型电池容量为 250,000 FE。电炉容量为 10,000 FE，读取原版熔炼配方；速度以存储占比按
0.05 量化，满速每 tick 消耗 20 FE，基础进度为 100 tick。

## Menu 与网络安全

电池和电炉 Menu 同时验证方块类型、位置和原版 8 格交互距离；机器槽、玩家背包、快捷栏的
shift-click 范围显式划分，输出槽拒绝插入。Screen 只读取 Menu 同步值，所有客户端类均位于
`client` 包并仅在 `Dist.CLIENT` 注册。

`SetGhostFilterMessage` 只表达设置样本意图。服务端依次验证发送者、当前菜单接口、目标位置、
已加载区块、8 格距离、建造权限、槽位范围及 `stillValid`；任一条件失败均不修改状态。

## 阶段性交接闭环

本文件最初记录的两个临时边界已由后续大任务关闭：

- 电炉现使用 `magneticraft:crafting/electric_furnace`，其核心材料恢复为
  `magneticraft:brick_furnace`；早期的临时原版熔炉配方已删除。
- 电、热、流体与物流物理网络已迁移完成；Forge Energy 仍只是设备边界适配器，内部电气网络
  由独立求解器维护真值。

因此这些内容是历史交接记录，而不是当前发布缺口。最终范围和验收结果见
[首发可行性与验收报告](release-readiness.md)。
